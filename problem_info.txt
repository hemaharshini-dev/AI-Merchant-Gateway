# 1. Project Problem Statement

## Problem

The way e-commerce works today is primarily designed for **human buyers**.

A human visits a merchant's website, browses products, reads product information, checks prices and availability, adds products to a cart, enters checkout details, and completes payment.

AI agents change this interaction model.

An AI buyer may instead receive a high-level objective such as:

> "Buy two wireless keyboards for my team, under ₹5,000 total, preferably mechanical, and make sure they can be delivered to Hyderabad."

The AI buyer should be able to independently:

1. Discover merchants that can satisfy the request.
2. Understand their product catalog.
3. Compare products.
4. Understand merchant policies.
5. Check availability.
6. Calculate the final transaction amount.
7. Decide whether the purchase satisfies the buyer's constraints.
8. Request a transaction from the merchant.
9. Complete payment.
10. Receive confirmation.

However, allowing autonomous AI agents to transact introduces a new problem:

### **How can a merchant safely accept transactions initiated by AI agents?**

A merchant cannot simply give an AI unrestricted access to its payment system.

The merchant needs to control:

* maximum transaction amount
* daily spending limits
* permitted product categories
* permitted quantities
* discount limits
* merchant-specific policies
* human approval thresholds
* payment authorization
* transaction auditability

The AI agent therefore needs a **controlled commerce layer between the AI buyer and the merchant's payment infrastructure.**

---

# 2. Our Proposed Solution

We will build an **AI Merchant Gateway** that converts a conventional merchant into an **AI-ready merchant**.

The gateway exposes the merchant's:

* products
* prices
* inventory
* product attributes
* shipping information
* return policies
* purchasing constraints

in a structured, AI-consumable form.

An AI buyer interacts with the gateway using natural language.

The gateway's agent then:

```text
AI Buyer Request
       ↓
Intent Understanding
       ↓
Merchant Catalog Search
       ↓
Product Matching
       ↓
Constraint Validation
       ↓
Merchant Policy Evaluation
       ↓
Transaction Risk / Authorization Check
       ↓
Human Approval if Required
       ↓
Razorpay Order Creation
       ↓
Payment
       ↓
Transaction Confirmation
       ↓
Audit Trail
```

The key principle is:

> **The AI can recommend and initiate a transaction, but it can never bypass the merchant's transaction policies.**

# C. Merchant Policy Engine

This is one of the **most important differentiating components**.

Merchants define rules governing what AI agents can do.

Example:

```json
{
  "max_transaction_amount": 10000,
  "daily_spending_limit": 30000,
  "max_quantity": 5,
  "allowed_categories": [
    "Electronics",
    "Office Equipment"
  ],
  "max_discount_percent": 10,
  "human_approval_threshold": 7500
}
```

The policy engine evaluates every proposed transaction.

It should return something like:

```json
{
  "decision": "REVIEW",
  "allowed": false,
  "reason": "Transaction exceeds automatic approval threshold.",
  "requires_human_approval": true
}
```

**Do not let the LLM itself enforce these rules.**

The LLM can reason.

The deterministic policy engine should enforce.

That's an important architectural distinction.

# 8. Human-in-the-Loop

There should be three possible decisions:

### APPROVE

Transaction satisfies all policies.

```text
₹4,500
Limit: ₹10,000

→ Automatically approved
```

### REVIEW

Transaction is potentially valid but requires human approval.

```text
₹9,000
Automatic threshold: ₹7,500

→ Human approval required
```

### DENY

Transaction violates a hard rule.

```text
₹20,000
Maximum transaction: ₹10,000

→ Automatically rejected
```

This distinction is important.

A soft limit can produce:

> **REVIEW**

A hard limit can produce:

> **DENY**
